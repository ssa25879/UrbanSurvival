## 4. 책임과 데이터 흐름

### 입력 → 플레이어 → 총기

- PlayerInput은 Move(Vector2), AimScreenPosition(Vector2), FirePressed/FireHeld/ReloadPressed를 수집한다. 입력 생산과 소비 순서를 명시하여 MonoBehaviour Update 순서의 우연에 의존하지 않는다.
- 종료·사망 → Esc 처리 → UI 포인터 차단 → 이동·조준 → R → 새 클릭 → 연사 유지 순서를 보장한다. R이 유효하면 발사보다 우선하고, 무효이면 발사는 허용한다.
- PlayerMovement는 카메라의 XZ 평면 forward/right와 크기 제한 이동 벡터를 사용하고 Rigidbody가 위치·회전을 소유한다. 조준은 총구 높이 수평 평면을 사용한다.
- PlayerShooter는 요청만 Gun에 전달한다. Gun이 탄약·간격·재장전·명중을 소유한다. 재장전 시작 및 UI/정지/포커스 경계에서 버튼 해제를 요구한다.
- Gun의 발사 승인과 탄약 차감은 시각 효과 참조 유무와 독립적이다. 총구 경로 및 내부 장애물 검사를 먼저 수행하고 막히면 탄약을 유지한다.
- 새 API는 승인 여부를 반환하는 TryFire/TryReload, 실제 증가량을 반환하는 AddAmmo를 우선한다. 기존 Fire/Reload 호출부와 직렬화 연결을 확인한 후 최소 변경한다.
- 기존 void RestoreHealth/IItem.Use는 호출부 전체를 조사한다. 성공량·성공 여부가 필요한 경우 TryRestoreHealth/TryUse를 추가해 기존 진입점을 위임하는 방식과 반환형 변경의 영향을 비교하고, 선택한 계약을 해당 하위 계획에 명시한다.

### 정적 설정과 판 상태

- 기존 GunData/ZombieData를 확장한다. 신규 후보는 CharacterData, WaveData뿐이며 범용 능력치·이벤트 버스·DI 프레임워크를 만들지 않는다.
- 설정은 ScriptableObject, 변화하는 체력·탄약·진행 시간·배율 적용 결과는 인스턴스가 보유한다.
- 판 시작은 참조 확보 → 선택 검증 → 기본값에서 배율 계산 → 최대/현재HP → 총기 → HUD → 조작 활성화 순서다. OnEnable이 이 값을 다시 덮어쓰지 않도록 한다.
- 단순 비활성화/활성화와 새 판 초기화를 분리한다. 정지는 상태 차단 및 scaled time 정지로 처리한다.

### 적 → 웨이브 → 종료 판정

- Zombie는 개별 이동·공격·사망을 소유하고 ZombieSpawner는 예약 생성·생존 집합을 소유한다.
- 생성 성공 시에만 pending을 줄인다. pending=0, alive=0, 생성 작업 없음이 모두 참일 때 완료를 요청한다.
- 사망은 dead를 먼저 확정하고 피해·경로·콜라이더를 차단한 뒤 한 번 통보한다. 생존 집합 제거 성공 여부를 점수 중복 방어에도 사용한다.
- GameManager만 상태를 전환한다. 같은 프레임의 종료 요청을 모아서 플레이어 사망을 우선 확정하고, 패배와 동시 발생한 최종 클리어 보너스는 지급하지 않는다.
- UIManager는 사건과 초기 스냅샷을 표시한다. UI가 체력·탄약·점수를 직접 수정하지 않는다.

### 재시작과 정리

- 공통 PlayerRoot 및 플레이 영역을 같은 씬에서 재구성하는 기획을 우선한다. GameManager가 선택 캐릭터·무기를 보존한다.
- 재시작 전 생성·재장전 코루틴/타이머 취소, 이벤트 해제, 적·보급 정리, 입력 초기화, timeScale=1 복원 후 기준 데이터에서 다시 초기화한다.
- 별도 영속 매니저는 추가하지 않는다. UIManager.GameRestart는 직접 LoadScene 대신 GameManager의 재시작 요청으로 연결한다.
- 루트 Rigidbody/피격 Capsule은 A/B 공통으로 유지한다. 모델을 자식으로 바꿀 때 Animator 검색 위치와 OnAnimatorIK 콜백 소유자를 함께 검증한다. 기존 GetComponent<Animator>를 무조건 유지해서 모델만 바꾸지 않는다.

EditMode는 스탯·설정 검증·종료 우선순위 등 순수 규칙에 사용하고 PlayMode는 실제 Gun/PlayerHealth/Spawner, 물리·타이머·씬 수명에 사용한다. 구현 로직을 테스트에서 복제해 비교하지 않는다. 마우스 입력·애니메이션·UI 시인성·외형은 실제 플레이/화면 검증을 병행한다.

Unity MCP가 연결되면 프로젝트 경로를 먼저 확인하고 테스트 목록→필터 실행→완료 결과/콘솔을 확인한다. 배치 테스트가 필요하면 설치된 Unity 실행 경로를 실제로 확인하고 `-batchmode -projectPath D:\work\Zombie -runTests -testPlatform EditMode` 또는 `PlayMode`, 결과 XML·로그 경로를 사용한다. 동일 프로젝트를 연 에디터와 두 번째 프로세스를 동시에 열지 않는다. 이 문서 작성 중에는 테스트를 실행하지 않았다.

## 8. Superpowers 전체 스킬 적용표

전체14개 스킬의 적용 범위를 검토했다. 조건이 다른 스킬을 전부 지금 실행했다는 의미는 아니다.

| 스킬 | 이번 작업/후속 적용 |
|---|---|

| dispatching-parallel-agents | 플레이어/총기와 적/웨이브 읽기 감사를 독립 위임. 공유 파일 수정은 하지 않음 |
| systematic-debugging | 입력 우선순위·사망·보급 등의 호출 흐름을 추적하고 정적 근거와 실행 미검증을 구분. 수정 시 재현부터 시작 |
| writing-plans | 파일/책임·의존 순서·검증 단위 분해에 활용. 설계 검토 후 각 하위 실행 계획에 실제 테스트/최소 구현 코드·실행 명령을 구체화 |

## 9. 병렬화 범위와 착수 순서

- 현재 읽기 감사는 독립 영역별 병렬화했다. 실행은 P0→P1→P2→P3→P4→P5→P6→P7→P8 순서로 진행한다.
- P0의 에셋 출처 조사와 코드 분석은 병렬 가능하다. 공유 Unity 씬·프리팹·ProjectSettings 수정은 단일 담당자가 처리한다.
- P2 이후에도 Gun·PlayerShooter, P3 이후 GameManager·Spawner·UI처럼 공유 계약이 있는 작업은 이전 결과를 확인한 후 진행한다.
- 첫 실행 범위는 P0이다. 그 결과에 따라 P1~P4를 작은 실행 계획으로 확정한다. 전체 MVP를 한 번에 구현하는 계획으로 넘기지 않는다.
- 본 초안 검토와 실제 수정 전 백업 결정은 별개다. 승인 여부를 추정하지 않으며, 새로운 세부 동작이 기획과 충돌하면 변경 이유와 영향부터 제시한다.
